About

From attack results to assurance

LLMs and AI agents now retrieve information, call tools and act on behalf of users. When a model output can become a tool invocation, a data access or a code execution, one question matters more than any single attack result: how do we know an LLM or agent is secure enough?

Benchmarks, red teaming and collections of known attacks reveal vulnerabilities, but they give only partial evidence about the security of a system. STALA focuses on (i) developing systematic methods for testing the security of LLMs and agents, and (ii) translating the resulting evidence into meaningful security assurance — reproducible, interpretable and actionable evidence that can support real security decisions.

Gap 1

The testing gap

The attack surface is enormous and structured: multi-turn context, retrieval, memory, tool calls, permissions, long-horizon trajectories and other agents. Static benchmarks sample a tiny fraction of it. A low observed attack-success rate may mean a weak test campaign, not a secure system.

Gap 2

The assurance gap

Even a strong campaign produces finite evidence. If nothing succeeds in 10,000 trials, what remains untested? When the model, prompt, tools or memory change, which evidence still holds? A failure rate is not an assurance statement without its threat model, coverage and uncertainty.

  • How should we test?

    Move beyond a benchmark and an average success rate: generate attacks, explore agent trajectories and tool interactions, mutate prompts and environments, and adapt tests to what earlier tests revealed — fuzzing, red teaming, adversarial search, stateful, metamorphic and coverage-guided testing.

  • How do we know what has been tested?

    More tests are not automatically more evidence. Depending on the threat model, the denominator may be prompts, attack strategies, internal features, agent states, action sequences or tool capabilities. We seek useful notions of coverage, diversity and representativeness for probabilistic and agentic systems.

  • What assurance does the evidence support?

    Quantify uncertainty and residual risk, decide when more testing stops being informative, combine empirical and formal evidence, reason about rare but consequential failures, and understand how evidence transfers across model updates and composes across model, RAG, tools and runtime controls.

Call for Papers

Topics of interest

STALA welcomes work across the full path from test generation to deployment-oriented assurance, including but not limited to:

Testing & evaluation

  • LLM and agent security fuzzing
  • Red teaming and adversarial test generation
  • Adaptive and search-based security testing
  • Jailbreak and prompt-injection testing
  • Long-horizon and stateful agent evaluation
  • Vibe coding and secure code generation
  • Tool, API, and MCP security testing
  • RAG, memory, and context-poisoning evaluation
  • Multi-agent interaction and delegation testing
  • Test oracles, differential, and metamorphic testing
  • Test harnesses, benchmarks, and testbeds
  • Prompt-, attack-, and behavior-space coverage
  • Agent state, trajectory, action, and tool-use coverage

Coverage & assurance

  • Internal neuron, circuit, expert, and routing coverage
  • Test diversity, representativeness, and adequacy
  • Benchmark contamination and generalization
  • Failure-discovery rates and testing stopping criteria
  • Confidence and calibration of security evidence
  • Residual-risk and rare-failure estimation
  • Security reliability and probabilistic assurance models
  • Assurance and heterogeneous evidence aggregation
  • Combining testing with formal or runtime guarantees
  • Compositional assurance for agentic systems
  • Regression, transfer, and continuous assurance
  • Quantitative deployment and release criteria
  • AI-on-hardware security and assurance

In scope

New attacks that contribute a reusable testing methodology or reveal something general about test adequacy. Security-relevant safety failures tied to an explicit adversary, system boundary or enforceable property — adversarially induced unsafe actions, malicious instruction following, containment failure, data exfiltration, or violated runtime safety/security invariants.

Out of scope

General AI ethics, fairness, governance, alignment philosophy and policy work without a concrete testing or assurance contribution.

Submission formats

8pages

Full papers

Complete research contributions on testing, coverage or assurance. Excluding references.

4pages

Short, position & experience papers

Early methods, benchmark or dataset contributions, experience reports, negative results and technically grounded positions. Excluding references.

Negative results are particularly welcome when they show that an intuitive testing metric, benchmark or assurance interpretation is misleading.

Submission site: Opens soon — formatting and anonymisation instructions will be posted with it.

What reviewers look for

  • Evaluation novelty counts. A paper need not introduce a new vulnerability if it materially improves how failures are searched for, measured or interpreted.
  • A new attack shown on a small prompt collection is not sufficient on its own unless it contributes a general testing insight.
  • Testing papers should explain what general evidence their method produces; assurance papers should ground their claims in an explicit testing process or other concrete security evidence.
  • For assurance work, a clear link between the claimed quantity and the evidence available under the stated threat model.
  • Each paper receives at least three independent reviews where feasible, with PC discussion for borderline or divergent cases and explicit conflict-of-interest management. Artifact release is encouraged.

Panel discussion
What evidence would convince you that an LLM or agent is secure enough to deploy?
  1. Panelists start from a concrete deployment scenario.
  2. Each specifies the threat model, the testing they would require, the coverage they would consider sufficient, and the uncertainty they would still accept.
  3. The moderator changes one assumption — a new tool, a model update, expanded permissions.
  4. Which conclusions still hold? When must assurance be reconsidered?
