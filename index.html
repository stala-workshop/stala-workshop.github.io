About

From attack results to assurance

LLMs and agents retrieve information, call tools and act for users, so a manipulated output can become a tool call, a data access or a code execution. How do we know one is secure enough? STALA works on systematic methods for testing LLMs and agents, and on turning the resulting evidence into security assurance.

Gap 1 · Testing

What gets exercised

Multi-turn context, retrieval, memory, tool calls, permissions and long-horizon trajectories make the attack surface vast. Static benchmarks sample a sliver of it, so a low attack-success rate may mean a weak campaign rather than a secure system.

Gap 2 · Assurance

What the evidence supports

Even a strong campaign produces finite evidence. A failure rate is not an assurance statement without its threat model, coverage and uncertainty — and when the model, prompt, tools or memory change, some of it stops holding.

How should we test?

Adaptive search over prompts, trajectories and environments instead of benchmark replay.

What has been tested?

Coverage, diversity and adequacy measures for probabilistic and agentic systems.

What does it support?

Residual risk, uncertainty, stopping criteria, and evidence that survives model updates.

Call for Papers

Topics of interest

Testing & evaluation

  • LLM and agent security fuzzing
  • Red teaming and adversarial test generation
  • Adaptive and search-based security testing
  • Jailbreak and prompt-injection testing
  • Long-horizon and stateful agent evaluation
  • Vibe coding and secure code generation
  • Tool, API and MCP security testing
  • RAG, memory and context-poisoning evaluation
  • Multi-agent interaction and delegation testing
  • Test oracles, differential and metamorphic testing
  • Test harnesses, benchmarks and testbeds

Coverage & assurance

  • Prompt-, attack- and behavior-space coverage
  • Agent state, trajectory and tool-use coverage
  • Internal neuron, circuit and routing coverage
  • Test diversity, representativeness and adequacy
  • Benchmark contamination and generalization
  • Stopping criteria and failure-discovery rates
  • Residual-risk and rare-failure estimation
  • Probabilistic assurance and evidence aggregation
  • Testing combined with formal or runtime guarantees
  • Compositional and continuous assurance
  • Quantitative deployment and release criteria

In scope: new attacks that contribute a reusable testing methodology, and safety failures tied to an explicit adversary, system boundary or enforceable property.

Out of scope: AI ethics, fairness, governance and policy work without a concrete testing or assurance contribution.

Submissions

8pages

Full papers

Complete contributions on testing, coverage or assurance. Excluding references.

4pages

Short, position & experience papers

Early methods, datasets, experience reports, negative results, grounded positions.

  • Submission site: Opens soon — formatting and anonymisation instructions will be posted with it.
  • Negative results are welcome when they show that an intuitive metric, benchmark or assurance claim is misleading.
  • Reviewers separate attack novelty from evaluation novelty: improving how failures are searched for, measured or interpreted is a contribution in itself.
  • At least three independent reviews where feasible, with PC discussion for divergent cases. Artifact release encouraged.
  • Around 7–9 accepted papers, published by the Internet Society in the NDSS 2027 workshop proceedings before the workshop.

Panel
What evidence would convince you that an agent is secure enough to deploy?

Panelists start from one deployment scenario and name the threat model, testing and coverage they would require. The moderator then changes an assumption — a new tool, a model update, wider permissions — and asks which conclusions still hold.
